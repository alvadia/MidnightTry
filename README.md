# RL-дообучение последовательной рекомендательной модели: GPT-2 + Reward Model + REINFORCE/GRPO на KION

---

## 1. Данные и протокол

**KION (МТС)** - публичная копия `irsafilo/KION_DATASET` (interactions.csv):
`user_id, item_id, last_watch_dt, total_dur, watched_pct`.

| факт | значение | provenance |
|---|---|---|
| сырых событий | 1 594 519 (268 битых, хвост файла обрезан)
| период | 2021-03-13 … 2021-08-22
| пользователей в сыром виде | 567 555
| медиана `watched_pct` | 32.0; ≥99% у 26.3%; =0 у 13.3%
| после фильтра (users≥5, items≥5, убр.дупл. по (user,item)) | 84 511 пользователей, 773 896 событий, 6 459 объектов |

**Разбиение с учётом времени и без утечек** [`src/data.py`]: у каждого
пользователя события упорядочены по дате; последний событие - **test**,
предпоследний - **valid**, всё остальное - **train**. Префикс истории никогда
не содержит будущий объект; reward model обучена только на train-событиях;
RL трогает только train-контексты. Оценка ранжирования - полный каталог
(6 459 объектов), уже просмотренные экранируются для основных метрик.

Ограничение датасета: дата с точностью до дня, поэтому порядок событий
внутри одного дня у пользователя определяется порядком строк в файле.
Это мягкое допущение; в отчёте оно влияет только на несколько проц. пар.

## 2. Базовая модель (без RL)

GPT-2-архитектура: causal self-attention (ручная реализация, чтобы
left-padding не давал NaN), токены - id объектов, output head - tied
embedding. Конфиг локального CPU-прогона: 2 слоя, d=64, 4 головы, d_ff=256,
max_len=30, dropout 0.2, AdamW lr 3e-4, батч 256, 4 эпохи (отбор по valid NDCG).

Цель - стандартный next-item CE loss с teacher forcing на train-части
последовательности.

## 3. Reward model

Тот же трансформерный pipeline, скалярная голова - `sigmoid` - прогноз доли
досмотра следующего объекта по префиксу истории. Обучение по MSE по всем
позициям train-событий. Оценка на отложенной выборке (последнее событие
каждого пользователя, 84 511 примеров):

| метрика | reward model | наивный baseline (среднее `watched_pct` по объекту) |
|---|---|---|
| RMSE | 0.409 | **0.379** |
| Spearman с true | 0.116 | **0.376** |
| корреляция pred/true (Пирсон) | 0.097 | - |

Это важный негативный результат: **текущая RM хуже** наивного
предметного среднего на отложенной выборке. Причина - сильная шумовая
дисперсия `watched_pct` (один просмотр != предпочтение) и недообученность
компонентной модели из-за CPU-класса вычислений.

Калибровка по длительности объектов (квартили средней `total_dur`):

| квартиль длительности | pred RM | true mean |
|---|---|---|
| короткие (36–3688 с) | 0.513 | 0.345 |
| 3688–5250 | 0.523 | 0.467 |
| 5250–7382 | 0.530 | 0.551 |
| длинные (7382–163480) | 0.516 | 0.434 |

RM **систематически завышает долю досмотра коротких объектов** (0.513 vs
фактических 0.345) - это и есть канал reward hacking, использованный RL.

## 4. RL-дообучение

REINFORCE с batch-baseline и GRPO (G=4, advantage = нормировка внутри
группы). Анкер - KL(π‖π_base) по лог-вероятности сэмплированного действия с
коэффициентом `kl_beta`. 800 шагов, батчами по 64, lr 1e-5.

Варианты функции вознаграждения (все оцениваются RM на сэмплированном объекте):

| run | reward shaping | KL |
|---|---|---|
| kion_completion | r = RM(h, a) | 0.05 |
| kion_completion_nokl | r = RM(h, a) | 0 |
| kion_completion_norep | r = RM − 1·[a ∈ history] | 0.05 |
| kion_completion_poppen | r = RM − α·log1p(pop(a)) | 0.05 |
| kion_grpo | GRPO, r = RM(h, a) | 0.05 |

## 5. Главные результаты (тест, полный каталог, K=10) [Н]

| модель | Recall@10 | NDCG@10 | MAP@10 | RM-reward top1 | Rewatch@10 | Coverage@10 | Entropy |
|---|---|---|---|---|---|---|---|
| base (без RL) | **0.1129** | **0.0613** | **0.0454** | 0.5305 | 0.0905 | 0.0053 | 0.2985 |
| +completion (KL) | 0.1066 | 0.0564 | 0.0412 | 0.5416 | 0.0866 | 0.0048 | 0.2959 |
| +completion (KL=0) | 0.0833 | 0.0481 | 0.0373 | 0.5418 | 0.0707 | 0.0039 | 0.2952 |
| +completion_norep | 0.1104 | 0.0567 | 0.0402 | 0.5250 | 0.0898 | 0.0059 | 0.2991 |
| +completion_poppen | 0.1071 | 0.0541 | 0.0379 | 0.5152 | 0.0906 | **0.0073** | 0.3160 |
| +GRPO | 0.0740 | 0.0447 | 0.0355 | 0.5399 | **0.0654** | 0.0042 | 0.3001 |

**Как максимизируется вознаграждение.** Предсказанный RM reward top-1
поднимается с 0.5305 до ~0.542 (+0.011) у vanilla RL и GRPO, но рост
предсказанного вознаграждения не означает реального улучшения: Recall@10
падает на 6–34%, а реальный средний `watched_pct` порекомендованных объектов
(feat `mean_item_pct` в bias_analysis) почти не меняется (0.537 => 0.53–0.54).

**Чем отличаются рекомендации.** RL-модели сдвигают top-10 к более коротким
объектам: средняя продолжительность  11 950 с => 8 916 (KL=0) и 8 588 (GRPO).
Объекты, заново вошедшие в top-10 после RL, заметно короче средних по base и
почти не лучше по факту (new_items_mean_dur 5.2–5.7 тыс. с vs base 11.9 тыс.).
Это ровно тот эффект, что предсказывался в задании: RM переоценивает короткие
объекты, следовательно, RL эксплуатирует эту ошибку.

**Коллапс GRPO.** GRPO на 800 шагах роняет энтропию с 7.49 до 1.05
и KL до 3.5. В многошаговой генерации GRPO рекомендует уже виденное на 96–99%
шагов (см. далее), и модель выдыхается в один «беспроигрышный» по RM объект.

## 6. Многошаговая генерация (5 шагов) [Н]

Контекст = train-история, добавляем сгенерированный объект и повторяем.
`repeat_rate` = доля шагов, где сгенерированный объект уже был в контексте.

| модель | RM reward step1=>5 | repeat step1=>5 | logprob политики step1=>5 |
|---|---|---|---|
| base | 0.523 => 0.518 | 0.06 => 0.17 | −3.64 => −3.74 |
| completion (KL) | 0.525 => 0.529 | 0.07 => 0.21 | −3.57 => −3.49 |
| completion (KL=0) | 0.537 => 0.537 | **0.07 => 0.62** | −2.23 => −2.03 |
| poppen | 0.522 => 0.519 | 0.02 => 0.12 | −3.88 => −3.87 |
| GRPO | 0.545 => 0.544 | **0.11 => 0.99** | −0.26 => −0.15 |

**Что происходит при генерации вперёд.** Сгенерированный объект - это НЕ
реальное взаимодействие пользователя, но он попадает в контекст и дальше RM
оценивает вознаграждение уже на синтетической истории. У KL=0 и GRPO контекст
быстро заполняется повторами: RM, обученная на реальных последовательностях,
на таких off-manifold-контекстах даёт завышенные и почти постоянные значения.
Политика, не привязанная KL, уверенно возвращается к одним (logprob −0.15!) и
тем же коротким объектам. У poppen и base с KL дрейф мягкий: RM reward почти
не растёт, повтор умеренный. Вывод: оффлайн-оценка reward при многошаговой
генерации оптимистична из-за distribution shift; для реального использования
нужен rollout с реальными откликами (онлайн) или world-model/пессимистичная RM.

**`poppen` даёт полезный компромисс**: Reward@10 падает сильнее (0.515), но
Coverage@10 растёт почти в 1.4× (0.0073 против 0.0053), Entropy максимальна,
Rewatch не растёт, а Recall/NDCG деградируют лишь на 5%/11% против base - т.е.
штраф за популярность переносит рекомендации в длинный хвост без обвала
релевантности. Это единственный вариант, где RL что-то улучшил по diversity.

## 7. Переносимость метода на Yambda (Яндекс Музыка)

Полный цикл (base => RM => RL completion, KL=0.05) прогнан на подвыборке
**Yambda** `sequential/50m/listens.parquet` (стриминг с HF, кат. 300 событий
на пользователя): 5 946 пользователей, 1 431 224 прослушивания, словарь 53 377
треков. Награда - `min(played_ratio_pct,100)/100`.

Base-модель на 53k-словаре при CPU-классе вычислений **сильно недообучена**
(Recall@10 = 0.0003) - это ограничение окружения, а не метода. Тем не менее RL-
дообучение дало неожиданные по сравнению с KION результаты:

| модель | Recall@10 | NDCG@10 | RM-reward top1 | Rewatch@10 |
|---|---|---|---|---|
| base | 0.00034 | 0.00014 | 0.6315 | 0.00875 |
| +completion (KL) | **0.00050** | **0.00021** | **0.6780** | 0.00918 |

Здесь рост предсказанного вознаграждения (+0.046) совпал с ростом
релевантности (+46% Recall, +50% NDCG) при слабой базе: RL вытянул модель из
недообученного состояния в сторону действительно дослушиваемых треков, а не
только эксплуатировал ошибки RM. Но есть нюансы:
* RM на Yambda тоже слабая - Spearman с true = −0.011 (почти нулевой), RMSE
  0.409 ≈ наивному baseline 0.413; т.е. выигрыш по метрикам идёт не потому,
  что RM хорошая, а потому что RL работает как доп. обучение на dense-сигнале
  доли прослушивания.
* Многошаговая генерация деградирует одинаково у base и RL: `repeat_rate` step1=>5
  0.01=>0.96 (base) и 0.005=>0.935 (RL) - на длинном горизонте обе модели
  скатываются в повторы, а RM-reward остаётся завышенным (0.71 на всех шагах).
  Distribution shift никуда не делся.

**Вывод по переносимости**: знак эффекта RL (релевантность-вознаграждение
согласованы или нет) зависит от того, насколько база недообучена и насколько
RM ловит реальный сигнал, а не от самого алгоритма RL. На KION (сильный
бейзлайн, а RM находит уязвимости) достигается компромисс; на Yambda (слабый
бейзлайн) возникает незначительное улучшение. Это согласуется с тезисом
задания: рост вознаграждения сам по себе не гарантирует улучшения, и наоборот.

## 8. Компромисс релевантность - вознаграждение

На этой модели увеличить предсказанный RM reward без заметного падения Recall
**не удалось**. Все варианты, поднявшие предсказанный reward выше 0.54,
потеряли ≥6% Recall. Функция награды и KL определяют результат:
KL=0 => reward +0.011 при −26% Recall (сильный взрыв);
GRPO => reward +0.009 при −34% Recall (уход в повторы);
norep с KL => reward держится 0.525, Recall почти базовая (−2%)
- штраф за повтор не дал модели уходить в один и тот же ответ;
poppen => сознательный отказ от reward ради разнообразия.

Настройки RL важнее самой функции: tiny lr и KL-анкер у completion(KL) сохранили
поведение близким к бейзлайну, но и reward почти не вырос. Основная узкая горловина
это слабая RM: пока RM хуже наивного baseline, RL оптимизирует шум и ошибки
калибровки.

## 9. Воспроизведение

Локально (CPU, py3.14, torch 2.14):

```bash
cd rlrec_kion
# данные: data/kion/interactions.csv (из https://github.com/irsafilo/KION_DATASET)
../.venv/Scripts/python.exe -m src.main --stage all --dataset kion --run-name kion_completion \
  --set processed_dir=data/processed_kion --set d_model=64 --set n_layer=2 --set n_head=4 \
  --set d_ff=256 --set max_len=30 --set base_epochs=4 --set rm_epochs=4 --set rl_steps=800
bash scripts/run_variants.sh           # остальные 4 RL-варианта
../.venv/Scripts/python.exe scripts/make_item_stats.py
../.venv/Scripts/python.exe scripts/analyze_bias.py
../.venv/Scripts/python.exe report/build_tables.py

# Yambda (стриминг с HuggingFace; требует pip install datasets):
../.venv/Scripts/python.exe -m src.main --stage all --dataset yambda \
  --run-name yambda_completion --set processed_dir=data/processed_yambda \
  --set d_model=64 --set n_layer=2 --set n_head=4 --set d_ff=256 --set max_len=30 \
  --set base_epochs=3 --set rm_epochs=3 --set rl_steps=800 --set kl_beta=0.05
```

GPU/полноразмерный прогон (KION d=128 + Yambda subsample): `notebooks/colab_rlrec.ipynb`
(архив кода для загрузки в Colab: `rlrec_kion_src.zip`). В Colab увеличены
ёмкость модели, число эпох/шагов RL, добавлены Yambda (sequential/50m listens.parquet).

Структура: `src/` (config/data/model/train/metrics/main), `scripts/`
(item stats, bias analysis, variants queue), `runs/<name>/` (config.json,
rl_log.json, eval.json, rmeval.json, policy_rl.pt), `report/` (tables.md,
bias_analysis.json), `notebooks/`.

**Главный вывод.** Перенос LLM-стиля RL (REINFORCE/GRPO + reward model) на
рекомендации воспроизводит известный риск: RM-reward растёт в основном за
счёт ошибок самой RM (переоценка коротких объектов, любовь к повторам), а
не за счёт качества рекомендаций. Содержательный положительный результат
удалось получить только там, где функция награды явно ограничивает этот канал
(`norep` удерживает Recall, `poppen` увеличивает diversity). Без сильной,
хорошо откалиброванной RM и без multi-step/онлайн-оценки RL-дообучение
рекомендательного трансформера опасно.

Контраст двух датасетов уточняет тезис: на KION (недообученная RM реально
хуже наивного baseline, сильная база) RL-оптимизация награды конфликтует с
релевантностью; на Yambda (база сильно недообучена из-за CPU-класса вычислений)
та же награда-доля-прослушивания сдвигает и reward, и Recall вверх. Знак
эффекта определяется тем, ловит ли RM реальный сигнал и насколько база
недообучена, а не выбором REINFORCE/GRPO - что и является главным исследовательским
результатом работы.
